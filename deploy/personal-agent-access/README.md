# Candidate deployment: personal SCM agent

Preparation only. No deployment or live permission changes are performed by these files.

1. Retain and verify a backup of Gateway configuration and its state volume. Keep the existing model credentials, read-only broker, plugin mounts and knowledge volume. Never copy one person's history, USER.md or memory into another workspace.
2. Generate a private candidate with `prepare_config.py --base <private-current-config> --origin <HTTPS-agent-origin> --out-dir <private-new-release-directory>`. The source is not modified. Validate the output with the pinned OpenClaw 2026.9.8 image (`config validate --json`). It preserves the approved read-only tools and model configuration. No per-person accounts or manifest are maintained: first authorized access reconciles the native agent and role.
3. Stage the candidate config in a Linux private writable **directory** mount. OpenClaw's supported native admin RPC persists roles/agent entries and requires atomic rename/chmod. Mounting the config file read-only or on a Windows filesystem cannot support this operation. Preserve ownership of the existing state volume. Remove stale `OPENCLAW_GATEWAY_TOKEN` / shared-token injection before activating trusted-proxy. The generated password is local maintenance only, never sent to a browser.
4. Build the bridge Dockerfile and publish/pin its immutable digest at release time. Merge the example into the existing reviewed compose; replace `gateway` with its actual service key. Use its network namespace so all native/admin HTTP/WS stays on loopback. Publish **only bridge port 5182** through the existing TLS ingress; remove any direct native Gateway port route. Do not mount Docker socket. An externally reachable native Gateway is a release blocker.
5. Supply private bridge environment from its example. Use HTTPS for the SCM API, exact HTTPS origins, the service credential matching the API, the maintenance-password file, `/state` as the native state root and the approved `scm-personal` template. Native model/provider defaults remain the approved existing ones; do not export credentials to personal workspaces or clients. Do not set `TESTING=true` in production.
6. Use exactly **one bridge replica and one persistent SQLite volume**. The fixed container name prevents Compose scaling. Separate independent SQLite disks are unsupported: they would break one-use handoffs and session continuity. Back up the volume as sensitive authentication state. Expired sessions are purged. Scaling requires a reviewed shared transactional store; do not deploy multiple instances behind a load balancer.
7. Deploy API and frontend with their new flags still false, then bridge/native config. A controlled initial restart is required to switch current token/off settings to trusted-proxy/hybrid. Later personal provisioning uses supported hot paths. Set frontend public build origin exactly and API signing/service secrets independently (at least 32 bytes). No database migration or new SCM capability is required.
8. Before enabling the flags, verify two users, own-only history, rejected foreign files, no native admin access, stale handoff rejection, and removal of the effective SCM capability while the same browser socket stays open. Confirm no new command reaches OpenClaw after revocation. Only then enable the entry. UAT approval remains human. Native 2026.9.8 personal session scopes deny HTTP previews (including own files) and outgoing downloads; the UI can show a secondary missing-operator.read warning. Keep that limitation explicit and never broaden global read scopes as a workaround. This release does not certify Office/ZIP analysis or file downloads.

Rollback: disable the new API/frontend flags and stop new bridge sessions, retain personal state/history and replay DB. Restore the verified prior native config/ingress and existing owner access during the approved deployment window. Do not delete personal state or replay records as a rollback shortcut. Existing role assignments in SCM are unchanged by deployment.
